# Provider-Neutral Delivery Orchestration

The **orchestrator** owns the delivery decision flow but does not edit implementation code. A host may conduct DEFINE and specification conversations remotely, then dispatch the executable plan to installed local or remote harnesses. A human operator acts as Product Owner during initial intent definition and specification refinement; agents execute, verify, audit, and self-correct work in bounded Git worktrees.

1. **DEFINE** — Capture business outcomes, scope, non-goals, constraints, and decision owner. MANDATORY COMPLETION GATE: Create or link the tracker item via `dev issuetracker create --title "<title>" --body "<body>" --type <feature|story|task|bug> --json` (or `gh` fallback) initializing status to **`01 Define`** (or `Backlog`) BEFORE proceeding to Stage 2 (**SPECIFY / GRILL**) or Stage 3 (**PLAN**). Do not generate technical `implementation_plan.md` or dispatch code execution until the tracker item exists. Read [github-pipeline-integration.md](../../references/github-pipeline-integration.md).
2. **SPECIFY / GRILL** — Inspect the target repository and relevant Central and Project Knowledge entries. Challenge contradictions, risks, scope boundaries, and acceptance conditions with the user. Update the tracker specification (`dev issuetracker comment <id>` / `dev issuetracker set-phase <id> --phase 02-spec`) and set project board status to **`02 Spec`**. Read `grill-with-context` when source-backed challenge is needed.
3. **PLAN** — Create minimal dependency-aware cohesive delivery slices, not artificial microtasks. Construct a Directed Acyclic Graph (DAG) of cohesive delivery slices with explicit file path boundaries. Publish technical `implementation_plan.md` for the **IMPLEMENT** phase with interactive user review request (`RequestFeedback: true`). Each task packet defines fields in [task-packet.md](references/task-packet.md), including worktree provenance, assigned persona, dependencies, and path boundaries. Read [autonomous-rework-loop.md](references/autonomous-rework-loop.md) for DAG scheduling rules. Set project board status to **`03 Plan`** (`dev issuetracker set-phase <id> --phase 03-plan`).
4. **DISPATCH** — Create dedicated feature branch (`dev forge branch create <branch-name> --base main` or `git checkout -b`) and Git worktree for each slice. Set project board status to **`04 Execute`** (`dev issuetracker set-phase <id> --phase 04-execute`). Select and assign the slice to the designated agent persona (`developer`) specified in [agent-personas.md](references/agent-personas.md). The executor retains the slice context end-to-end to understand local code, implement, use TDD where relevant, run and fix the verification loop, and return reviewable diff evidence.
5. **COLLECT / VERIFY** — Collect each executor's change summary, verification result, evidence, and blockers. Run the target repository's deterministic verification gate (e.g. configured verification command in `AGENTS.md`, `just verify`, or test runner). Record verification evidence in `walkthrough.md`. If verification fails, initiate the autonomous rework loop (up to `max_retries: 3`), feeding failure logs directly back to the executor persona. An executor stops and returns the slice when a material boundary issue emerges. Read [autonomous-rework-loop.md](references/autonomous-rework-loop.md).
6. **REVIEW** — Open Pull Request (`dev forge pr create --title "<title>" --body "Closes #<id>\n\n<summary>" --head <branch> --base main`) and update project board status to **`05 Review`** (`dev issuetracker set-phase <id> --phase 05-review`). Conduct multi-persona review (`quality-engineer`, `solution-architect`, `security-auditor`) auditing TDD assertion strength, DDD domain purity, Hexagonal layer isolation, and OWASP security risks. Update `walkthrough.md` and submit PR review verdicts (`dev forge pr review <pr-number> --verdict approve --body "<notes>"`). Read [agent-personas.md](references/agent-personas.md). If a reviewer returns `CORRECT_EXECUTE` or `CORRECT_PLAN`, re-dispatch autonomously to the executor with correction payload until approved or retry limit (N <= 3) is reached.
7. **SHIP / RETURN** — Once changes pass all verifications and persona reviews, commit verified changes, push the branch to remote origin (`git push`), and create exactly one durable **Delivery Record** (Issue / PR reference) for the cohesive delivery slice before publishing its **Review Request** on the short-lived task branch. Update project board status to **`06 Ship`** (`dev issuetracker set-phase <id> --phase 06-ship`). Present the work to the Product Owner with interactive merge authorization instructions (`dev forge pr merge <pr-number> --strategy squash --delete-branch`). Upon merge, the issue auto-closes, remove the task Git worktree (`git worktree remove <worktree-path>`), prune stale remote tracking branches (`git remote prune origin`), and project item moves to **`07 Improve`** (`dev issuetracker set-phase <id> --phase 07-improve`) where the `improve` skill captures retrospective learnings. During `07 Improve`, explicitly audit if any fallback to `gh` occurred due to missing `dev forge` or `dev issuetracker` capabilities; if so, create an improvement item to extend `devcli`. If no follow-up improvement is required, the delivery cycle completes as **Done**. Executors do not merge, approve, or force-push protected default branches; the user retains merge authority.
